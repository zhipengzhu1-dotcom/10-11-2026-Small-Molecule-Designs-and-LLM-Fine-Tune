# Context

Replicating s1 (arXiv 2501.19393) at small scale. Spec: GitHub issue #1.

## Factory logs

- **Event**: one JSON line with `ts`, `run`, `agent`, `type` and the type's required fields (issue #1). Written only through `factory/log.mjs`, which stamps `ts`, `run` and `agent`.
- **Event contract choices**: three points where the stream departs from a literal reading of issue #1's API contract, each deliberate and tested (issues #21, #62). `agent.start`'s `parent` is always `orchestrator` (see Agent id). Decision events have `run: null` (see Decision log). `agent.stop` carries no `transcript` field in the stream, though older activity files have one (see Lifecycle hooks).
- **Activity file**: `factory/agents/<run-id>/<agent-id>.jsonl`. One per agent; an agent writes only its own. Committed by the merge script, not by the agent.
- **Decision log**: `factory/decisions.tsv`, pstack show-me-your-work format, append-only, written only by the orchestrator, one row per `npm run decide -- <phase> <decision> <why> <evidence> <result>`. That runs the installed pstack's `log.sh` (found through `installPath`, never a cache path) and puts the session transcript pointer, `transcript:<session>@<ISO time>` at the transcript's latest entry, first in the evidence; rows written before spec #52 carry the older `~/.claude/projects/<slug>/<session>.jsonl @<HH:MM:SS>Z`. Every evidence item that starts with `<kind>:` must be a **Pointer** that resolves, or the row is refused and nothing is written; other items are prose. The session is `--run`, else `FACTORY_RUN`, else the run marker's run; with none of them it refuses rather than guess from the newest transcript, which can be a concurrent session's. Its `--state`, `--supersedes`, `--withdraws`, `--corrects` and `--closes` flags build the **Claim state** and **Relation phrase** parts of a row (`factory/claim.mjs`). Committed by the merge script. In the stream its rows are `type: "decision"` events with `agent: "orchestrator"` and `run: null`. This is deliberate (issue #21): the TSV has no run column, and the run marker can't stand in for one, because it is local state that each run overwrites. Decision events are the only events with a null run; a reader places them in a run by `ts`. Each also carries `line`, the row's line number in the file, which is how the audit and later rows ("supersedes line 15") cite it.
- **Pointer**: one item of evidence in the one grammar the factory has: `file:<path>[:<line>[-<line>]]` (repo-relative, or `~/` for the home folder; a gitignored path does not resolve, since only one checkout has it), `commit:<sha>` (7 to 40 hex digits, a commit of the repo), `transcript:<session>@<ISO time>` (a prefix of an entry's timestamp in that session's transcript), `issue:<n>` and `url:<http(s) URL>` (taken as given, since they need the network). Text with no `<lowercase word>:` prefix is prose. `factory/pointer.mjs` is the one parser (`parsePointer`) and resolver (`resolvePointer`); the decision writer, the trail check and the audit all use it.
- **Decision time**: a decision row's `ts` is when the row was written, the only time the log can vouch for. It can trail the moment of deciding by seconds to hours; the transcript pointer in its evidence gives that moment. Order between rows comes from their pointers, not from comparing `ts`.
- **Supersedes**: a later decision row replaces an earlier one and takes over everything the earlier row was disputing, so superseding a correction never brings back the row it corrected.
- **Withdraws**: a later decision row retracts an earlier one without replacing it. A withdrawn row can come back if its withdrawal is itself withdrawn.
- **Corrects**: a later decision row fixes only an earlier row's evidence (which file, line or source it cites). The decision itself stands; a correction is not a contradiction.
- **Closes**: a later decision row settles an earlier open row, such as a handed-off question its ticket has since answered, so the earlier row no longer reads as dangling.
- **Relation phrase**: how a decision row names the rows it supersedes, withdraws, corrects or closes: `<relation> line N: ` at the start of the decision cell, `<relation> line N (part): ` when it touches only one clause of row N, and several joined by `, ` (supersedes, withdraws, corrects, closes, in that order). N is the earlier row's line in `factory/decisions.tsv` (the header is line 1). Written only by `npm run decide -- --supersedes|--withdraws|--corrects|--closes <N>[ (part)]`, which refuses a line past the log's last row and a phrase typed into the decision by hand. The `supersedes line N:` rows of spec #1 already follow it.
- **Claim state**: the first word of a decision row's `result`, written `<state>` or `<state>: <text>` (`npm run decide -- --state <state>`), from a closed list mapped to SACM v2.3 `assertionDeclaration` (OMG formal/23-05-08, §11.8):

  | State | SACM | Use it when the row |
  |---|---|---|
  | `adopted` | `asserted` | makes a decision that stands, or records an action done (merged, fixed, filed) |
  | `open` | `needsSupport` | leaves something undeveloped: started, pending, handed off, flagged |
  | `assumed` | `assumed` | takes something as true without support, to be checked later |
  | `given` | `axiomatic` | records a rule that needs no support, such as the user's instruction or a binding constraint |
  | `cited` | `asCited` | restates a claim made elsewhere (a paper, another log) without re-arguing it |

  `pass` and `fail` are check results, not states. SACM's `defeated` is never written: it is derived from later rows' relations. The trail check enforces the claim state and the relation phrases on rows from 2026-10-13 on (`CLAIM_RULES_FROM` in `factory/claim.mjs`); earlier rows stay valid as written.
- **Event stream**: `readStream()` in `factory/read.mjs`. Merges every activity file and the decision log by `ts`. Tests and the dashboard read only this. It throws on a corrupt line or an event filed under the wrong agent or run. It passes events through as written, except that it leaves the legacy `transcript` field out of `agent.stop` (see Lifecycle hooks).
- **Audit**: `factory/audit/<run-id>.tsv`, one verdict (`ok` or `superseded`) per decision-log row, with the pointers the auditor checked. Written by the run that audited the log against the transcripts (pstack show-me-your-work), through `npm run audit` (`factory/audit.mjs`): `show <line>` prints a row and its session since the session's previous row, each line led by its transcript pointer, and `add <line> ok|superseded` appends a verdict only once the trail check's rules pass on it. Transcripts are read through `factory/transcript.mjs` (`npm run transcript -- <session-id>` prints one timestamped line per message, tool call and answer to AskUserQuestion), not a parser of its own. A wrong row is never edited: a later row supersedes it, and the audit names that row's line.
- **Trail review**: `factory/audit/<run-id>.review.md`, the cross-family model's review of the trail, made with `npm run audit -- review --run <run-id>`, which sends the audited rows, the audit and the session digest through `factory/review-qwen.mjs` (local `qwen3.5:9b`, thinking off in code). Its `reviewed by <model>` line names the reviewer. Its flags go in the Attention section of the run's final reply. It is a sanity check, not a gate.
- **Trail check**: `npm run check:trail` (`factory/checks/trail.mjs`). Writes a `check` event named `trail`. Passes when the log is append-only against its git history, every row is well formed (no empty cell; a phase that is `start` or a lowercase slash path on the log's one tree), every row has a verdict whose pointers resolve (a `file:` pointer deleted since resolves at the commit that added its audit row, named in the evidence), and every audit has a non-Claude review. From 2026-10-13 on, a row's `result` must start with a **Claim state** and its relations must be well-formed **Relation phrases** naming earlier rows. Rules about the real log live here, not in unit tests.
- **Ticket graph**: a `ticket.graph` event, the spec's ticket graph as the frontier command (`npm run frontier -- <spec>`, `factory/frontier.mjs`) read it from GitHub: `spec` (the spec or map issue number) and `tickets`, one `{ number, state, status, blockers }` per child, where `state` is GitHub's (`OPEN`/`CLOSED`), `status` the frontier's and `blockers` the issues still open among its native blocked-by edges. The frontier writes one per call, as agent `orchestrator`, during an orchestrated run only, so the graph can be rebuilt from the logs without calling GitHub (issue #59). `spec`, `tickets` and the numbers in them are JSON values, not strings.
- **Check ticket**: the optional `ticket` on a `check` event, the issue number of the ticket the check concerns, so per-ticket gates see the orchestrator's own checks. Every check takes `--ticket <n>` (or `#<n>`), and `log.mjs check ... ticket=<n>` takes the same; either is recorded as the number `<n>`, and anything else is refused (issue #59).
- **Default run**: an event written with no `--run` and no `FACTORY_RUN` (by `log.mjs` or a check) is filed under the run marker's run, so the merge script commits it.
- **Manual run**: with no run marked either, a check files its event under run `manual`, and `log.mjs` refuses for want of a run.
- **Factory root**: the main checkout, never the cwd. Resolved from `--root`, then `FACTORY_ROOT`, then `CLAUDE_PROJECT_DIR`, then the repo holding `factory/log.mjs`. Subagents run in worktrees, but their events land in the main checkout.

## Fetch page

- **Fetch page**: `npm run fetch-page` (`node factory/fetch-page.mjs [--root <repo>] [--port 4174]`), served on `127.0.0.1` only. Lists each **open** `fetch.failed` ref: no later `artifact` event with that `ref` field or a path under `research/refs/<ref>/raw/`.
- **Title**: the `fetch.failed` event's optional `title` field, else the `title` column of `research/refs/catalog.tsv` (keyed by a `bibkey`, `key` or `ref` column), else none.
- **Drop**: `POST /drop?ref=<ref>&name=<file>` with the file as the body. Saved to `research/refs/<ref>/raw/<sanitized name>` (never overwriting), then an `artifact` event (`kind: ref`, `ref`) is written as agent `fetch-page` in the run of the `fetch.failed` event it closes. Refused: a ref with no open failure, a ref that isn't a plain folder name, a foreign `Host`, a cross-site `Origin`.

## Viewer

- **Viewer**: `npm run viewer` (`node factory/viewer.mjs [--root <repo>] [--port 4175]`), served on `127.0.0.1` only, read-only (anything but `GET` gets 405). A quick stand-in for the dashboard (piece C): the page polls `GET /state?run=<run>` every 2 seconds and shows a swimlane timeline of the run's agents, the agent network, a 3-D graph of the decision log, the latest result of each check, the agents table and the event list. Black, white and grey only; status is told by fill (solid PASS, grey ISSUES, outline BLOCKED or unknown, pulse running).
- **Agent network**: every subagent of every run (or only the picked run) in 3-D around a hub per run for its orchestrator. A running agent (no `agent.stop`, in the newest run) is bright and pulses in a halo; a stopped one is filled the way it ended. Links, each a layer the page can hide: `dispatched` (the hub to each agent), `ticket` (agents whose task names the same ticket, chained in start order), `builds` (an agent whose instructions name another ticket, to the latest agent on that ticket that started before it), `files` (two agents with an `artifact` event at the same path).
- **Task**: what an agent was asked to do. The stream doesn't carry it, so the viewer reads it, read-only, from Claude Code's subagent transcript `~/.claude/projects/<slug of the root>/<run>/subagents/agent-<id>.jsonl`: `task` is the `description` in the `.meta.json` beside it, `tickets` the `#N` it names (with no description, the first `#N` of the first message), `mentions` every other `#N` of the first message. The path is built from the run and agent ids, never from a path in the stream. No transcript, no task: the agent shows its role. A stand-in until agents log their task (#21).
- **Decision graph**: tree links join a root, each phase folder and each decision to its parent. Cross-links, each a layer the page can hide: `supersedes` (a decision to the row it replaces), `mentions` (a decision to the `ticket-N` phase of a `#N` it names, outside its own phase), `evidence` (a node per source cited in two or more phases, linked to each citing decision; hidden by default).
- **Viewer files**: `factory/viewer/` holds `page.html` and the scripts `app.js`, `ui.js`, `layout.js`, `swimlane.js`, `force.js`, `graph.js`, `crew.js`, served by name only at `/assets/<name>`. `layout.js` has no DOM and no three.js (decision and crew graphs, 3-D force layout, swimlane geometry), so `node:test` covers it. `force.js` is the 3-D graph both diagrams share; `graph.js` and `crew.js` say what each draws. The diagrams load three.js `0.170.0` and its OrbitControls add-on from jsDelivr through an import map; when it can't load, they show a note and the decision tree falls back to a plain list.
- **State**: `summarize(events, run, taskOf)`. `run` defaults to the newest run, which is never `manual` while a session run exists: a check run by hand must not end the session in the page. `crew` lists every subagent of every run, with its task and the files it wrote. An agent with no `agent.stop` is `running`. Decisions have no run, so a run's timeline takes the decisions made between its first and last event; the newest run takes every later one too. The tree covers the whole decision log. If `readStream()` throws, `/state` returns 200 with the message in `error` and the page shows it as a banner.

## Run id and agent id

- **Run id**: the orchestrator's Claude Code session id. Hooks take it from the payload's `session_id`. The orchestrator passes its own with `FACTORY_RUN` or `--run`.
- **Agent id**: Claude Code's `agent_id` from the hook payload. The orchestrator's is `orchestrator`. Hooks record `parent: "orchestrator"`, deliberately (issue #21). The payload has no parent field, and Claude Code fires `SubagentStart` and `SubagentStop` only for agents the orchestrator session spawns. An agent a subagent spawns gets no lifecycle events and no writer command, so it never appears in the stream. (Its parent is the `parentAgentId` in Claude Code's `subagents/agent-<id>.meta.json`, which is written after `SubagentStart` runs.)
- **Run marker**: `factory/run.json` in the factory root, `{"run": "<run-id>", "branch": "<integration branch>"}`. Gitignored local state. The orchestrator sets it when a run starts with `node factory/run-marker.mjs start --run <run-id> --branch <integration branch>` (run also from `FACTORY_RUN`); it refuses while a tracked file outside the factory logs has uncommitted changes, since mergers work in that checkout. It clears it at the end with `node factory/run-marker.mjs stop`. The merge script reads the run and the integration branch from it with `readMarker(root)`.
- **Merge script**: `npm run merge -- <branch> [-m <message> | -F <file>]` (`factory/merge.mjs`), run in the main checkout on the marker's integration branch. Commits the run's factory paths (`factory/agents/<run>/` and `factory/decisions.tsv`, nothing else), then merges `<branch>` with `--no-ff`. The factory commit copies the message's Co-Authored-By trailers. Messages reach git through a file, so their newlines survive. `npm run merge -- --factory-only` (same `-m`/`-F`) commits those paths without merging, for close-out. Refuses with no run marked or off the integration branch. It is the one step that commits the factory's own writes, so mergers need no commit-factory-paths-first step.
- **Orchestrated run**: a session whose id the run marker names. Only it is logged by the lifecycle hooks. With no marker, or a marker naming another run, a `SubagentStart`/`SubagentStop` writes nothing and injects no writer instructions, so meta sessions (reflect, review, close-outs) leave `factory/agents/` alone. A payload with no `session_id` is still recorded, under run `unknown`, while any run is marked.
- **Lifecycle hooks**: `.claude/settings.json` runs `factory/hooks/subagent.mjs` on `SubagentStart` and `SubagentStop` (they fire in the orchestrator session), during an orchestrated run only. It writes `agent.start` / `agent.stop`; a field the payload lacks becomes `unknown`. The stop `status` is the first `PASS`, `ISSUES` or `BLOCKED` in `last_assistant_message`. When that has none, the hook reads `agent_transcript_path` and uses the last `SubagentHandback` report, then the last assistant text block. If neither has one, the status is `unknown`. `agent.stop` carries the contract's fields, `role` and `status`, and the **report**. The subagent's transcript is `<transcripts dir>/<run>/subagents/agent-<agent>.jsonl`, so the event doesn't name it. `agent.stop` events written before issue #21 also carry a `transcript` field with that path. It isn't part of the contract, so `readStream()` leaves it out and the dashboard can't come to depend on it (issue #62); the activity files keep it, since they are append-only.
- **Report**: `agent.stop`'s `report` field (spec #52, story 8), the subagent's hand-back text, so reports can be searched without reading transcripts. It is the text the status was read from; with no status anywhere, the `SubagentHandback` report, else `last_assistant_message`, else the last assistant text block. It is kept whole up to 65,536 (64k) characters; a longer one is cut to that and the event gets `report_truncated: true` (a JSON boolean). A stop with no hand-back text has neither field. Stops written before spec #52 have no `report`.
- **Agent description**: the `description` the orchestrator gives an `Agent` launch, in the grammar `<role> #<n|-> <what>`: one lowercase role word (hyphens allowed, no closed list), then `#` and the ticket number it serves, or `#-` for work with no ticket (audits, reviews, reflections), then what it does. Examples: `implementer #53 pointer grammar`, `audit #- trail rows 77-87`. It carries role and ticket because `subagent_type` can't: nearly every launch is `general-purpose`. One parser, `parseDescription()` in `factory/description.mjs`, returns `{ role, ticket, what }` (`ticket` null for `#-`) or null, for the hook below and the dispatch event (spec #52).
- **Description hook**: `factory/hooks/agent-description.mjs`, run by `.claude/settings.json` before every `Agent` call (PreToolUse). In the orchestrated run only, it blocks a launch whose description breaks the grammar (exit 2, with the grammar and examples in the message). Other sessions, and a subagent's own `Agent` calls (payload has `agent_id`), are not checked.
- **Writer command**: on `SubagentStart` the hook injects `additionalContext` telling the subagent its agent id, run id and the exact command for its own events:
  `node "<main>/factory/log.mjs" --root "<main>" --run <run-id> --agent <agent-id> <type> key=value ...`
- **Context tokens**: `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` of the session's latest main-thread reply, skipping sidechain (subagent) entries and API-error placeholders. `contextTokens(file)` in `factory/transcript.mjs`.
- **Context meter**: `factory/hooks/context-meter.mjs`, run by `.claude/settings.json` on every `UserPromptSubmit` and `PostToolUse`. In the orchestrated run only, it injects one line, `Context meter: N tokens in context (latest main-thread reply).`, read from the payload's `transcript_path`. Other sessions, a subagent's tool calls (payload has `agent_id`) and a transcript with no reply yet get nothing.

## Local models

- **VRAM cap**: 8 GiB (8,192 MiB) of GPU memory, the RTX 5060 budget, for every model run on the RTX 5090 (decision log line 3). It is separate from the parameter limit (models under 8B) on the same line.
- **VRAM delta**: a model's real footprint, the rise in `nvidia-smi` memory.used when it loads alone. Measure it with `npm run vram -- <model>...` (`scripts/vram.mjs`). Ollama's `/api/ps` `size_vram` reads low and is no measure of the cap (issue #38).
