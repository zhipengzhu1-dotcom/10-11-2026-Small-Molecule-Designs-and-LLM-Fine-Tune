# W3C PROV as the factory's provenance graph

Issue #35, map #26. Written 2026-10-11. Desk research: the W3C PROV documents and the Open Provenance
Model paper, checked against the factory's own files at commit `af3bdea` (main). The worked example ran a
throwaway Node script, kept outside the repo, over the real logs.

Citation keys (full list at the end): **DM** = PROV-DM, **CON** = PROV-CONSTRAINTS, **O** = PROV-O,
**OV** = PROV-Overview, **LNK** = PROV-Links, **JSON** = PROV-JSON, **OPM** = Open Provenance Model v1.1.
Factory files are cited as `path:line`.

## 1. The structure

**Nodes.** Three kinds: an *entity* is "a physical, digital, conceptual, or other kind of thing with some
fixed aspects"; an *activity* is "something that occurs over a period of time and acts upon or with
entities"; an *agent* "bears some form of responsibility for an activity taking place, for the existence of
an entity, or for another agent's activity" [DM §2.1.1, §2.1.3]. One agent subtype fits all of ours:
`prov:SoftwareAgent`, "running software" [DM §5.3.1].

**Edges.** In the core every relation is binary and named in the past tense [DM §2.1, Table 2]. The core
seven are `wasGeneratedBy` (entity→activity), `used` (activity→entity), `wasInformedBy`
(activity→activity), `wasDerivedFrom` (entity→entity), `wasAttributedTo` (entity→agent),
`wasAssociatedWith` (activity→agent) and `actedOnBehalfOf` (agent→agent) [DM Table 2]. Every edge points
from the *influencee* to the *influencer*, and all of them are subtypes of `wasInfluencedBy` [DM §5.3.5,
Table 7]. The extended set adds the ones we need: `wasInvalidatedBy` [DM §5.1.8], the derivation subtypes
`Revision`, `Quotation` and `PrimarySource` [DM §5.2.2-5.2.4], `specializationOf` [DM §5.5.1], `hadMember`
[DM §5.6.2] and, from a Note, `mentionOf` [LNK §2]. So a PROV instance is a typed directed multigraph
G = (V, E) with V = Ent ∪ Act ∪ Agt and every edge labelled from a fixed set R of about a dozen relation
names. Agents may also be entities or activities [DM §5.3.1], so the three sets can overlap.

**Order, not clocks.** PROV puts no total time order on anything. It defines five instantaneous events
(generation, usage, invalidation, start, end) and a preorder *precedes* on them, "like Lamport" [CON §2.2,
§6.2]. An instance is valid when its normal form exists, when the graph of *precedes* and *strictly
precedes* edges has no cycle through a strict edge, and when no type or impossibility constraint fails
[CON §7.1]. The rule we lean on most is Constraint 42: if `wasDerivedFrom(e2, e1)`, then gen(e1) strictly
precedes gen(e2) [CON §6.2.2]. Timestamps don't settle ordering [CON §6.2], but an application "MAY flag"
times that disagree with the event order [CON §6.2].

**No transitivity.** PROV infers *no* transitive closure. "There is no inference stating that
wasDerivedFrom is transitive" [CON §5.3], and `wasInformedBy` is shown not to be transitive [CON §5.2].
OPM, PROV's predecessor, does define one: multi-step `wasDerivedFrom*` "is the transitive closure of the
edge 'was derived from'" and "expresses that artifact a2 had an influence on artifact a1" [OPM §6.2,
Def. 11]. OPM's inferences "do not allow process elimination" [OPM §6.1], and PROV-DM gives the reason:
an activity that used e1 and generated e2 does *not* imply that e2 was derived from e1 [DM §2.1.2].

**Provenance of provenance.** A *bundle* is "a named set of provenance descriptions, and is itself an
entity" [DM §5.4.1], typed `prov:Bundle` [DM §5.4.2]. Example 41 merges two observers' bundles into a third
that `wasDerivedFrom` both and `wasAttributedTo` the aggregator [DM §5.4.2]. `mentionOf(e2, e1, b)` makes
e2 a specialization of e1 whose extra aspect is "the bundle b containing some descriptions of e1"
[LNK §2]. OPM's earlier *account* is "a description at some level of detail as provided by one or more
observers". An account view is legal only "if it is free of cycle of 'was derived from' edges and if it
contains at most one 'was generated by' edge per artifact" [OPM §7, rules 2 and 11].

**Serializations.** PROV-DM is the conceptual model. PROV-O (OWL2, RDF), PROV-N and PROV-XML serialize it
[OV §2]. PROV-JSON is a W3C *Member Submission*, not a Recommendation: one top-level object with a map per
record type (`entity`, `activity`, `agent`, one per relation name, `bundle`), each keyed by identifier
[JSON §2].

## 3. Questions it answers for the orchestrator

Each query is a breadth-first walk over typed edges, one per orchestrator decision made today.

| Orchestrator decision today | Query on the PROV graph | Answer it gives |
|---|---|---|
| **Pick the next ticket** (frontier, #34) | for each claim that is INCONCLUSIVE or NOT VERIFIED, the size of its forward closure over `wasDerivedFrom*` [OPM Def. 11], counting live brief rows and live decisions | which unchecked claim carries the most weight downstream, so verifying it is worth the most (value of information) |
| **Merge** a branch | backward lineage of each artifact on the branch: does every source resolve to a committed entity? Does any entity have two generations [OPM §7 rule 11]? | flags work built on scratchpad or worktree files, and parallel writes of one file (the L46 bypass; see §4) |
| **Re-dispatch** after a verdict flips | forward closure from the old verdict entity, then `wasAttributedTo` / `wasAssociatedWith` on each hit | which brief rows and decisions to recheck, and which agent or role made them |
| **Supersede** a decision row | `wasRevisionOf` + `wasInvalidatedBy` on the old row, then rows that `used` it | that the old row is no longer live, and what cited it |
| **Declare done** | every brief row's backward lineage reaches a primary source (`main.tex`, the clone at `77272c6`, a dataset card) with no invalidated link and no missing generation; and Constraint 42 holds on every derivation edge [CON §6.2.2] | a machine check that the brief rests on evidence, not on prose |

**What invalidation means.** PROV's `wasInvalidatedBy` ends an entity's *lifetime*: it is "the start of
the destruction, cessation, or expiry of an existing entity" [DM §5.1.8]. It doesn't say an entity is
false. A verdict flip is therefore a *revision*: the new verdict `wasRevisionOf` the old one, and the old
one `wasInvalidatedBy` the re-verification activity. The claim text stays, as claims.md:9 already
requires. Everything in the old verdict's forward closure becomes *suspect*, not invalid. That closure is
our own OPM-style query, because PROV licenses no transitive inference [CON §5.3].

**PROV-O or plain JSON?** Plain JSON in PROV-DM's vocabulary is enough. PROV-O's OWL axioms don't make
`wasDerivedFrom` transitive: the ontology file at `https://www.w3.org/ns/prov-o` declares no
`owl:TransitiveProperty`. So an RDF store would still need a property-path query for lineage, and PROV-O
"does not specify how to encode Bundles in RDF" [O §4]. Our audit files are bundles, so that gap matters.
PROV-JSON's layout (a map per record type, keyed by id [JSON §2]) is a good shape for an in-memory index,
but it is a Member Submission, not a standard. Use it as a guide, not as a contract.

**Bundles and our audit files.** The match is close, with one nuance:

- `decisions.tsv` is a bundle attributed to the orchestrator.
- Each activity file is a bundle attributed to its agent. CONTEXT.md:8 already enforces one writer per
  file, and `read.mjs:59` throws on a foreign event.
- `audit/<run>.tsv` is a bundle *about* the decision bundle. Its rows are `mentionOf(row, decisions.tsv)`
  with a verdict [LNK §2]. Its `superseded` verdicts become the `wasRevisionOf` edges.
- `review.md` is provenance of the audit (DM §2.2.2, Example 14, the decision-maker case), attributed to
  `qwen3.5:9b`.
- The nuance: PROV-DM Example 41 has an aggregator merge bundles into a new one [DM §5.4.2], and that is
  what `readStream()` does. The merged stream is a third bundle derived from all the others, so it should
  never be cited as evidence in its own right.

## 4. Worked example

Script: `build.mjs` in the session scratchpad (`…/scratchpad/prov/`), never committed. It imports
`readStream()` from `factory/read.mjs` and also reads `decisions.tsv` (for line numbers),
`audit/99ae39b6-….tsv`, `verification.md` and `brief.md`. It needs no dependencies and runs in 63 ms,
Node start-up included.

**Size of today's graph.** It holds 247 stream events, 73 decision rows, 73 audit rows, 182 claims and
the brief's C-citing rows. That gives **884 nodes** (716 entities, 120 activities, 48 agents) and **1,776
edges**: 644 `wasDerivedFrom`, 515 `hadMember`, 147 `wasGeneratedBy`, 120 `wasAssociatedWith`, 90
`specializationOf`, 85 `used`, 73 `mentionOf`, 45 `wasAttributedTo`, 45 `actedOnBehalfOf`, 6
`wasRevisionOf`, 6 `wasInvalidatedBy`. The 6 text supersessions match the audit's 6 `superseded_by` cells
exactly ([55,15] [56,18] [57,28] [58,35] [59,38] [60,51]).

**Invalidation: suppose C-04 flips to NOT VERIFIED.** Today C-04 ("the base model is
Qwen2.5-32B-Instruct, supervised fine-tuned on s1K") is VERIFIED (verification.md:76). Forward closure over
`wasDerivedFrom` at fragment level:

```
claim:C-04 -> brief:P-10 (brief.md:150, pre-tokenized data)
claim:C-04 -> brief:P-12 (brief.md:157, base model)
claim:C-04 -> brief:L26 (departure item 1, "Base model")
            -> file:brief.md#L26-37 -> dec:L60 project/replication/open-decisions (open)
live decisions downstream: L60
```

L51 also cites item 1, but only as prose (`'Where the plan departs' items 1, 2 and 8`). The script can't
see it, and it doesn't need to: L51 is superseded by L60.

Walk the same claim at *file* level instead, letting a row lift to its whole file. That is what you get
when evidence cites `research/s1/brief.md` with no line. Now 7 live decisions come back: L27 and L57
(through `claims.md`), L39 and L41 (through `verification.md`), L50 (cites the whole `brief.md`), L60, and
**L37**. L37 is a false positive: the aime fetch at 21:50:47 "depends on" the brief only because both hang
off the single orchestrator activity of run `14c93a90`. That activity *used* `brief.md` in its check at
22:16:31 and *generated* the aime file 26 minutes earlier. This is the inference PROV-DM forbids, where a
use and a generation by one activity are taken as a derivation [DM §2.1.2]. It also breaks event order:
the effect is generated before its "cause" is used [CON §6.2]. **Lesson:** model each orchestrator check
and decision as its own activity, and follow only `wasDerivedFrom` (plus time-filtered `used`→`generated`
pairs) when computing invalidation.

Two smaller results. C-10 (traces from Gemini) reaches only P-02, with no live decision downstream. C-22
and C-29, already NOT VERIFIED, reach P-06 and P-07. Those rows already carry the caveat in their
`assumption` column (brief.md:146-147), so nothing is left unflagged.

**Backward lineage of P-06 ("AIME years in training pool", brief.md:146).** Hand-completed. [stream]
marks edges that came from `artifact` events, [prose] edges read from a file's text, [missing] edges with
no record at all.

```
brief:P-06  -> claim:C-22, claim:C-137                    brief.md:146 location column
claim:C-22  -> main.tex L198 (primary source)              claims.md row C-22
verdict:C-22 NOT VERIFIED -> data/add_aime.py:7-8 @77272c6  verification.md:94; clone pinned by decision L25
verdict:C-137 NOT VERIFIED -> data/add_aime.py:8            verification.md:209
verification.md  generated by a3b5f34f0 @21:51:09            [stream]
  derived from review-a.md (aa77b1f85 @21:40:32),
               review-b.md (aef9eae54 @21:42:23)            [prose] verification.md:3-7; generations [stream]
  both derived from claims.md (a9f6203f5 @21:22:04)          [prose]; generation [stream]
claims.md derived from main.tex (a9f6203f5 @21:15:47)        [prose] claims.md:3; generation [stream]
brief.md    generated by orchestrator from a80af6a42's draft [missing] only decision L50 says so
```

Every generation time is later than its source's, so Constraint 42 holds. The one break in the chain is
`brief.md` itself, the row the orchestrator would cite when declaring done.

**OPM account rule on the real stream.** Two files have two `wasGeneratedBy` edges:
`research/refs/hendrycks2021measuringmathematicalproblemsolving/summary.md` and
`research/refs/lightman2023letsverifystepstep/summary.md`. Each was generated by reader `ae5fa48fe` at
22:00:25 and again by `orchestrator` at 22:03:14. That breaks "at most one 'was generated by' edge per
artifact" [OPM §7 rule 11], and it is exactly the write-block bypass that decision L46 flagged (branch
`fc72f4c`, unmerged). In PROV terms these are two entities, two versions of one path. A one-generation
check over the stream would have caught it with no human reading.

## 5. Cost and fit

**Complexity.** Building the graph is one pass over the stream and three markdown files: O(V + E).
Forward or backward closure from one node is a BFS, also O(V + E). At 884 nodes and 1,776 edges that is
milliseconds (63 ms with Node start-up). At "thousands later", say 10k nodes and 30k edges, a single
closure is still sub-millisecond. Even all-pairs closure, O(V·(V+E)) ≈ 4×10⁸ steps, stays in seconds and
is never needed. Checking Constraint 42 on every derivation edge is O(E). Full PROV-CONSTRAINTS validity
(normalization, unification [CON §7]) is far more machinery than we need. It runs on CPU only, so the
8 GB VRAM cap doesn't apply.

**Libraries.**

- `prov` (Python): MIT license, v3.2.2 released 2026-09-18. It covers every PROV-DM record type, reads
  and writes PROV-N, PROV-JSON, PROV-JSONLD, PROV-XML and PROV-O, and converts to and from a NetworkX
  `MultiDiGraph`. Source: GitHub API and README of `trungdong/prov`, read 2026-10-11.
- ProvToolbox (Java): its `license.txt` is MIT-style permission text, though GitHub reports
  `NOASSERTION`. It has a `modules-validation` directory. Source: GitHub API and repo tree of
  `lucmoreau/ProvToolbox`, read 2026-10-11.
- No maintained JavaScript PROV library turned up (GitHub search for `prov-json`).

Both would add a runtime (Python or the JVM) to a repo that is Node-only (`package.json`). The ticket
rules out new dependencies, and the throwaway script (about 200 lines of plain JS, most of it parsing) already covers what we use.
Recommendation: no library. If a PROV-N or RDF export is ever wanted for outside readers, `prov` is the
mature choice. It can run through `uvx` as a one-off tool without becoming a dependency.

**How it reaches the orchestrator (#25).** A digest line, computed on read like the viewer's state:

```
prov: 884 nodes 1776 edges | 1 ungenerated (research/s1/brief.md) | 2 double-generated (refs/*/summary.md: ae5fa48fe, orchestrator) | 0 order violations | suspect after last flip: P-10 P-12 L60
```

Plus two queries a future CLI could offer: `--impact <id>` (forward closure, live rows only) and
`--lineage <id>` (backward, with [stream], [prose] and [missing] marks).

**Dashboard.** Replace layout.js's `evidence` and `supersedes` link kinds with PROV relation names, and
keep `tree` and `mentions` as non-PROV kinds. On select, highlight a node's forward and backward
closures.

**Feeding the high-dimensional node model (#26, #27).**

- *Typed edges.* PROV's dozen relation names are the relation set R for knowledge-graph embeddings, about
  11 types on today's graph. They are directed, and their meaning is fixed by a standard rather than by
  us.
- *Node features.* PROV class and `prov:type` one-hot, generation time, invalidated flag, verdict,
  `result`, in-degree and out-degree per relation, ancestor and descendant counts, depth to a primary
  source, and whether the lineage has a [prose] or [missing] link.
- *Constraint on embeddings.* Any learned link score must respect Constraint 42: never predict
  `wasDerivedFrom(e2, e1)` when e1 was generated after e2. Each account view must also stay free of
  derivation cycles [OPM §7 rule 11]. Both are cheap to test on any proposed link.
- Node text (decision, claim) is #28's job, not PROV's.

## 6. Verdict

**ADAPT.** Take PROV-DM's node classes and its fixed relation vocabulary as the semantic layer of the
factory graph. Derive the graph on read from the logs we already write. Use bundles and `mentionOf` for
the decision log, activity files and audits. Add OPM's multi-step closure as our own query, and keep two
checks: Constraint 42 ordering and one generation per entity.

Skip PROV-O and RDF, full PROV-CONSTRAINTS normalization, and any library. They add machinery without
answering a question we have. PROV-O doesn't even make derivation transitive or encode bundles.

The adaptation pays off once three gaps close:

1. Orchestrator writes log an `artifact`.
2. `artifact` events carry `used=`.
3. Decision evidence uses the audit's typed pointer grammar.

Until then, file-level reachability over-approximates. In the worked example it returned 7 live decisions
where the fragment-level walk found 1.
